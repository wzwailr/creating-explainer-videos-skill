# v2.0.1 Release Integrity Design

## Objective

Ship a reproducible `v2.0.1` patch release that corrects the runtime contract and proves the real browser-render-to-media path. The Git tag, GitHub assets, PyPI artifacts, and any npm Registry artifact must all come from the same green commit.

## Compatibility contract

- Python 3.9+ lifecycle commands (`install`, `update`, `verify`, `rollback`, `uninstall`, and extension listing) continue to work without Node.js.
- JavaScript project, preview, render, and media commands require Node.js 22 or newer because the pinned HyperFrames `0.8.15` package declares `node >=22`.
- The npm package declares `engines.node >=22`; CI covers Node.js 22 and 24 instead of claiming Node.js 18 render support.
- `doctor` must not download packages. It probes `npx` itself and reports pinned HyperFrames as `on-demand` when no installed binary is present. `readyFor.render` accepts an installed HyperFrames binary or the supported `npx` path, but never accepts Node.js below 22.

## Real-render proof

Add a deterministic, short fixture that runs the real production adapters:

1. create an actual generated project;
2. write a measured one-scene cue contract;
3. invoke pinned HyperFrames through `renderVideo`;
4. render the dedicated cover with Chrome or Edge;
5. generate a local synthetic WAV with FFmpeg;
6. mux H.264 video and AAC audio;
7. run the real `auditMedia` ffprobe, full-decode, black-frame, frozen-frame, silence, contact-sheet, and delivery checks;
8. assert `automatedPassed === true` while retaining `release_candidate_pending_human_listen`.

The fixture uses no paid provider, remote media asset, or human-release bypass. HyperFrames may be resolved from npm on the first run; the rendered page itself remains local and network-free.

## Release provenance

- Bump all distributable identities to `2.0.1`.
- Commit and push the complete change before creating a tag.
- Require the main-branch CI for that exact commit to pass.
- Create `v2.0.1` on that same commit and require its tag CI to pass.
- Build npm tarball, Skill zip, Python wheel, and Python sdist from a clean checkout at the tag.
- Audit and smoke-test those exact files, create one SHA-256 manifest, then publish/upload those unchanged bytes.
- Do not move or rewrite the historical `v2.0.0` tag. Document its supersession by `v2.0.1`.

## Registry truthfulness

- PyPI `2.0.1` is published only after local wheel/sdist audits and tag CI pass.
- npm publication is attempted only after `npm whoami` succeeds. If authentication or publishing-level 2FA remains unavailable, the release must continue to advertise GitHub tarball installation and explicitly state that the npm Registry package is unavailable.
- Release success is reported separately for GitHub, PyPI, and npm; one registry cannot stand in for another.

## Out of scope

Theme-specific scene primitives, automatic knowledge-to-visual conversion, executable TTS providers, and expanded sample films are `v2.1.0` work. They must not be mixed into this compatibility patch.
