# v2.1 Theme Visual DSL and Executable TTS Design

## Status

Approved for implementation on 2026-08-31. This document defines v2.1.0 of the generic `creating-explainer-videos-skill` package.

## Goal

Turn the v2.0 executable scaffold into a topic-responsive production system without weakening its evidence, permission, or human-release boundaries.

v2.1 adds two capabilities:

1. A bounded visual program that lets an Agent describe the actual objects, relationships, state changes, and cue-bound motion required by a topic.
2. Executable voice adapters that can synthesize canonical narration, measure the resulting audio, resume safely, and write the timing contract consumed by animation.

The package remains a general explainer-video Skill. AI topics and the existing Chinese series are examples and presets, not the package identity.

## Non-goals

- Do not generate arbitrary HTML, CSS, JavaScript, shell commands, or remote assets from the visual program.
- Do not turn declarative extensions into executable hooks.
- Do not bundle fonts, voices, GSAP commercial plugins, or media without redistribution rights.
- Do not claim a topic-specific visual program is automatically pedagogically correct.
- Do not mark a rendered candidate publishable without complete human listening to the exact hashed artifact.
- Do not implement every possible diagram or TTS provider in v2.1.

## Architectural choice

Use a core-owned declarative visual compiler plus a reviewed voice-adapter registry.

Rejected alternatives:

- Raw topic HTML/GSAP modules are powerful but allow arbitrary execution, weaken portability, and make validation superficial.
- A full general-purpose scene-graph engine would delay the usable release and duplicate browser layout capabilities.
- Treating voice profiles as executable extensions would make a copied declarative extension an execution authority, contradicting the v1 security boundary.

## System flow

```text
brief + evidence + mechanism map
              |
              v
canonical narration -----> executable voice adapter
              |                    |
              |                    v
              |           cue audio + hashes + measured durations
              |                    |
              +--------------------+
                          |
                          v
                  canonical cue clock
                          |
                          v
scene specification + visual-program.json
                          |
                          v
              validate -> compile -> renderer
                          |
                          v
              HyperFrames -> FFmpeg -> QC
```

## Visual program contract

### File and compatibility

New projects contain `visual-program.json`. Existing v2.0 projects without that file continue to use the generic scene scaffold. If the file exists and `complete` is true, `build` must validate and compile it. Invalid completed programs block the build; the renderer must never silently fall back.

```json
{
  "schemaVersion": 1,
  "template": "spatial-chamber",
  "complete": true,
  "scenes": []
}
```

The selected template must match `project.json` and `scene-spec.json`.

### Scene model

Each visual scene contains:

- `id`: the matching scene ID.
- `cueIds`: narration cues owned by the scene.
- `layout`: `free`, `flow`, `compare`, `stack`, `network`, or `timeline`.
- `elements`: bounded semantic elements with explicit normalized geometry.
- `actions`: cue-bound deterministic changes.

Normalized geometry uses `x`, `y`, `width`, and `height` in the inclusive range zero to one. The compiler converts these values to CSS percentages. This makes the program frame-size independent and lets validation catch overflow before rendering.

### Element vocabulary

| Type | Required data | Purpose |
| --- | --- | --- |
| `group` | `id`, `frame` | Visible region, chamber, ledger, lane, or conceptual boundary |
| `text` | `id`, `text`, `frame`, `role` | Title, label, body, formula, code, metric, or caption-adjacent text |
| `node` | `id`, `label`, `frame`, `role` | Entity, state, token, process, input, output, warning, or evidence object |
| `shape` | `id`, `shape`, `frame`, `role` | Rectangle, circle, diamond, or line-based visual anchor |
| `connector` | `id`, `from`, `to`, `route`, `role` | Directed relation, data flow, cause, branch, or feedback loop |
| `asset` | `id`, `src`, `alt`, `frame` | Local SVG, PNG, JPEG, or WebP asset inside `assets/` |
| `annotation` | `id`, `text`, `target`, `frame`, `role` | Explanation, correction, boundary, or callout tied to another element |

Element IDs are unique inside a scene. Connectors and annotations must reference existing IDs. Text is HTML-escaped. Local assets are path-normalized, must stay under the project `assets/` directory, and cannot use URLs, data URIs, scripts, or SVG event handlers injected through the program.

### Action vocabulary

| Kind | Effect |
| --- | --- |
| `appear` | Opacity and scale enter from a stable hidden state |
| `exit` | Opacity and scale leave to a stable hidden state |
| `move` | Translate an element between explicit normalized offsets |
| `focus` | Raise emphasis while de-emphasizing non-target peers |
| `draw` | Reveal connector/path progress deterministically |
| `pulse` | Apply a bounded emphasis pulse without wall-clock animation |
| `replace` | Cross-fade one target out and another target in |

Every action declares `cueId`, `target`, optional `with`, `at`, and `duration`. `at` and `duration` are cue-relative fractions from zero to one. The compiler resolves them to measured local scene time. An action cannot run outside its cue, reference another scene, or use implicit randomness.

### Compilation

`validateVisualProgram(projectRoot)` returns structured errors and warnings without writing files.

`compileVisualProgram(projectRoot)` validates the program, resolves cue timing, emits escaped semantic DOM/SVG markup, and produces deterministic action metadata. Template CSS maps semantic roles onto its visual language. The existing template motion controller remains responsible for template-wide establishing motion; the visual program controller applies topic actions on top of it.

Commands:

```text
explainer-video-skill visual validate <project> --json
explainer-video-skill visual compile <project> --json
explainer-video-skill visual preview <project> --output <html> --json
```

`build` calls the same compiler. `preview` writes an explicit preview target and does not render or publish media.

## Executable voice adapters

### Core registry

Executable adapters live in the reviewed runtime, not inside declarative extensions. v2.1 ships:

- `edge-tts`: real network synthesis through a host-installed Python `edge-tts` module.
- `fixture-tts`: deterministic local WAV generation for tests only. Its output is marked `testOnly` and cannot satisfy the real-audio release gate.
- `host-command`: an explicitly trusted external executable that implements protocol version 1.

The existing `neutral-technical-zh` voice extension selects defaults and pronunciation policy. It does not gain execution authority.

### Authorization boundary

- `edge-tts` requires `--allow-network` on every uncached synthesis run.
- A `host-command` adapter that declares network access requires `--allow-network`.
- An adapter whose cost is `paid` or `unknown` requires `--authorize-provider-cost` before an uncached request.
- Cached, hash-verified cues may be reused without new provider authorization because no provider is invoked.
- Credentials remain in the provider environment or host credential store. They never enter CLI arguments generated by the Skill, project JSON, cache metadata, logs, manifests, or distribution artifacts.

### Canonical request protocol

Each cue is normalized before synthesis. The adapter receives a JSON request file containing:

```json
{
  "protocolVersion": 1,
  "requestId": "sha256-derived-id",
  "cue": {
    "id": "C01",
    "text": "canonical narration",
    "language": "zh-CN",
    "voice": "zh-CN-YunxiNeural",
    "rate": "+0%",
    "pitch": "+0Hz"
  },
  "output": {
    "audioPath": "absolute host path under .publish/narration",
    "format": "wav",
    "sampleRate": 48000,
    "channels": 2
  }
}
```

The host-command executable is called with `--request <path> --response <path>`. Its response records status, audio path, provider task ID when applicable, and diagnostics. The core verifies the response schema, requested output path, non-empty audio, media duration, and file hash. The adapter executable and configuration are explicitly selected by path and hash; installing a declarative extension cannot create this configuration.

### Synthesis, cache, and recovery

The core computes an input hash from adapter ID, canonical text, language, voice, rate, pitch, and output format. A cache entry is reusable only when the input hash, output file size, and output SHA-256 all match.

For uncached cues:

1. Enforce provider authorization.
2. Synthesize one cue with at most three attempts for a retryable failure.
3. Normalize to 48 kHz stereo PCM WAV and remove leading/trailing silence.
4. Measure speech duration with ffprobe.
5. Persist the cache entry atomically before moving to the next cue.

After all cues are available, the core concatenates them with deterministic gaps, writes `.publish/narration.wav`, writes measured timing, and calls the existing caption/TTS importer. Default gaps are 0.12 seconds inside a scene, 0.28 seconds between scenes, and 0.9 seconds at the end.

`recover` uses the same engine and cache. It does not submit a cue whose valid artifact is already present.

Commands:

```text
explainer-video-skill narration adapters --json
explainer-video-skill narration doctor <project> --adapter edge-tts --json
explainer-video-skill narration synthesize <project> --adapter edge-tts --voice zh-CN-YunxiNeural --allow-network --json
explainer-video-skill narration recover <project> --adapter edge-tts --voice zh-CN-YunxiNeural --allow-network --json
```

## Skill guidance

The Skill entrypoint routes an Agent to two new references:

- `visual-program-dsl.md` when converting a mechanism and measured cues into topic-specific scenes.
- `voice-adapter-protocol.md` when generating, configuring, or extending narration synthesis.

Instructions require the Agent to prefer semantic topic objects over decorative repetition, validate before compile, listen for pronunciation defects, and preserve authorization boundaries.

## Project-state integration

New v2.1 projects record `visual-program.json` as scene-design evidence. The real-audio stage accepts only non-test narration. Existing projects remain readable:

- Missing visual program: generic v2.0 scaffold remains available.
- Existing imported timing: remains authoritative.
- Existing declarative extensions and locks: remain API version 1.
- Existing renderer/media commands: retain their names and behavior.

The package version becomes 2.1.0; project, visual-program, adapter protocol, and extension API versions remain independently versioned.

## Validation and release gates

Automated tests must cover:

- Visual schema success and malformed IDs, geometry, references, paths, cue ownership, and action timing.
- Deterministic compilation and distinct topic markup across all three templates.
- Backward-compatible fallback for projects without a visual program.
- Canonical caption/TTS identity and underscore removal.
- Fixture adapter end-to-end audio, timing, cache reuse, and recovery.
- Edge TTS invocation construction and explicit network authorization.
- Host-command config hash, protocol validation, output confinement, and paid/unknown-cost authorization.
- CLI commands and fresh project scaffolding.
- Real browser render, cover, mux, ffprobe, and media audit.
- npm tarball, Skill ZIP, PyPI wheel, and PyPI sdist integrity and fresh-install smoke tests.

Release order:

1. Commit and push v2.1.0 source.
2. Wait for green main CI.
3. Create and push the signed version tag used by all distributions.
4. Build all artifacts from that exact tag commit.
5. Publish npm and PyPI only after local artifact audits pass.
6. Create the GitHub Release with checksums.
7. Download every public artifact and compare hashes or registry integrity to the local artifacts.

## Success criteria

v2.1 is complete only when a fresh installation can:

1. Create a project.
2. Validate and compile a topic-specific visual program.
3. Produce materially different semantic scenes under the three templates from the same bounded schema.
4. Generate real Edge TTS narration when explicitly authorized, or execute a trusted host adapter through the protocol.
5. Resume cached synthesis without repeating successful provider calls.
6. Rebuild animation from measured cue timing.
7. Render and audit a real MP4 while still stopping at human listening rather than claiming publish approval.
